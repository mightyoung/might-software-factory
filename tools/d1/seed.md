# D1 isolated tooling seed

`seed.java` creates a separate `d1seed` tenant and `d1foreign` tenant after the D1 migrations (currently V28). It never enables an application or grants a role in an existing tenant. Custody scopes have their own identifiers and link to organizations; they are not departments themselves. No tool or occupancy records are seeded.

Run with the project Java dependencies on the classpath, using the migrator credentials through private environment inputs. Required variables are `D1_DATABASE`, `D1_JDBC_URL`, `D1_OPERATOR_USERNAME`, `D1_OPERATOR_PASSWORD`, and `D1_SEED_ACK=isolated-d1-seed-only:<database>`. Only a localhost PostgreSQL 18 target named `msf_d0_d1_*_test` is accepted. Each `D1_SEED_PASSWORD_<ACTOR>` must contain a private UTF-8 password of 16–72 bytes; actor names are `KEEPER`, `READER`, `CREATEONLY`, `UPDATEONLY`, `NONKEEPER`, `OUTSIDE`, `ADMIN`, and `FOREIGNKEEPER`. Passwords are bcrypt encoded and never printed. Do not put them in command arguments or source files.

The seed takes the global authorization writer lock and commits the identity and authorization graph together. Repeated execution verifies the exact owned graph and supplied passwords. Changes to entitlements, role scopes, grants, keeper validity, identity status, or epochs cause failure and rollback; rerunning does not repair drift or reset passwords.

The ordinary reader has `tool.read` without keeper membership. The nonkeeper has all three tool permissions but cannot create or update. Create-only and update-only actors have their respective action and keeper membership without read permission. The outside actor operates in a different organization and scope. The admin has platform permission management only. Normal catalog visibility requires an active scope and `NORMAL` archive state; it makes no promise that an item is available to borrow. Occupancy belongs to D2.

`seed_graph_test.java` exercises the real seed against the unseeded owned core target within one transaction. It verifies two baseline graphs and rejects six authorization drift cases, then rolls back every fixture row. It requires the same private operator inputs and explicitly accepts only `msf_d0_d1_core_test`.

`permission_upgrade_test.java` is a separate real Flyway upgrade check. Its three explicitly named disposable targets start at a genuine V26 history: missing capabilities, compatible legacy NULL application metadata with existing role associations, and incompatible tuples. V27 is applied unchanged before V28. The check verifies ID and association preservation, no application activation or user grants, custom metadata preservation, and transactional rejection of resource/action/application conflicts. It requires private `D1_UPGRADE_SCENARIO` and `D1_UPGRADE_ACK=isolated-d1-upgrade-only:<database>` inputs in addition to the same operator connection inputs. It never repairs migration history or modifies the core/browser target.

## Real browser acceptance

From the repository root run `node tools/d1/browser.mjs` with the existing frontend Playwright dependencies and installed Google Chrome. First build the frontend with the HTTP adapter, serve that compiled output over loopback HTTPS, and proxy `/api` to the matching real backend using the D1 runtime account and seeded isolated database. Apply V28 and both the D0 base grants and D1 delta before starting; do not use the mock server for this check.

Provide private environment inputs: `D1_BROWSER_ORIGIN=https://127.0.0.1:<port>`, `D1_DATABASE`, `D1_SEED_ACK=isolated-d1-seed-only:<database>`, `D1_BROWSER_OUTPUT`, and the actor passwords described above. The output directory must be task-owned with mode 0700. The script checks the declared target and ACK; the operator must also verify that the HTTPS proxy and backend datasource actually point to that database. No credentials belong in source, command arguments, or committed reports.

This check creates uniquely named synthetic tool records and immutable audit/revision/receipt history, which it retains. It tests persisted reloads, two-tab version conflict, real server commit followed by deliberately dropped transport response and same-key recovery, read-only/create-only roles, and organization scope. Cross-tenant checks are in `ToolLedgerPostgresIT`. Screenshots and failure page text are private evidence and must be reviewed before sharing. Record the source manifest, final jar and frontend hashes, browser version, and V28 history alongside the result; a browser PASS alone does not prove artifact identity or migration coverage.
