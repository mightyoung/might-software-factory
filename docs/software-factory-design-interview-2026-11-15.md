| Q15 | 旧申请沿用提交时字段版本，发放前调整保存修订；新申请使用新版 | 新必填不阻断旧单归还；普通当前主数据按新版维护 |

沿用、不重新讨论的基线：电脑端优先；AI/开发者在代码中配置并经审查测试发布；主从同事务；稳定 ID 引用；历史快照不被改名或调岗覆盖；流程定义发布不可变、在途默认留旧版；缺权限或办理人不跳过；普通删除默认停用或归档。详见[公共设计](public-services-design.md#14-版本-v11-台账发布和性能约束补充)及[逻辑模型](logical-schema.md)。

## 3. 目标架构与实现边界

保留 Java/Spring 模块化单体、PostgreSQL、jOOQ/Flyway、既有 Flowable 和会话边界。本轮不更换技术栈。三类职责分开：

1. **定义与注册**：applicationregistry 负责版本化应用、实体、字段、动作、引用和导航登记；定义是描述，不直接授予权限或执行命令。
2. **通用台账运行能力**：提供按登记定义执行的查询、标准新增编辑、主从保存、引用查询及前端通用页面。建议使用独立的 ledger 模块，避免导航注册模块同时承载全部业务持久化。
3. **业务模块**：安全业务与工装业务分别拥有自身模型、规则和特殊动作，通过公开接口调用公共能力。公共模块不认识 finding 或 tooling 等具体业务。

浏览器通过统一台账组件读取公开定义；业务模块登记服务端字段/列映射、动作与策略。服务端绑定不向浏览器暴露表名、列名或可执行表达式。请求只能引用已登记的实体、字段和动作。

### 3.1 一份定义贯通哪些地方

| 定义部分 | 内容 | 使用方 |
|---|---|---|
| 身份与版本 | appKey、entityKey、定义版本、兼容信息 | 注册、API、缓存、历史解释 |
| 字段 | 稳定字段键、类型、可空、枚举、长度/精度等 | 服务端基础校验、查询及界面 |
| 场景规则 | 创建/编辑/读取场景中的可见、可写、必填、布局 | 表单与服务端输入约束 |
| 引用 | 目标实体、可选候选查询、引用权限、当前值或快照 | 联想、多选、详情、服务端关联校验 |
| 从属明细 | 行标识、字段、顺序/数量约束、所属聚合 | 主从表单、原子保存、并发控制 |
| 动作 | 标准操作或已登记业务命令、输入契约 | 按钮呈现、受控路由、命令调用 |
| 历史 | 哪些字段冻结、何时冻结、采用哪个版本解释 | 单据、审计与历史详情 |

领域规则如“工装是否可发放”继续由业务代码判定；它们不应被压成任意在线表达式。公开定义中的校验提示只改善交互，服务端执行完整规则。支持通过明确接口增加控件和业务校验，不要求全部业务页面均使用同一布局。

### 3.2 标准写入与特殊动作

标准保存只处理实体登记允许的输入。tenant、actor、ID、版本、流程绑定、占用状态等受保护字段不能由通用输入随意覆盖。乐观版本和定义版本分别检查，未知字段或不支持的定义版本必须给出明确错误。

- 工装档案的描述性字段可使用标准新增编辑；停用归档仍需业务守卫，不能把在借工装隐藏或释放。
- 借用申请及明细可复用主从表单、基础校验和保存组件；提交、修改已提交申请、撤销、发放、归还、接收、异常结案由工装模块显式命令控制。
- 发放后的明细和办理历史不能通过普通编辑接口修改。特殊动作可以复用内部标准校验/存储组件，但保有自己的授权、状态前提和事务边界。
- 当前隐患接口逐步适配公共能力，不先做全面替换；双确认、证据封存和既有事务行为保持独立验收。

所有业务写入继承既有安全事务协议，包括 root→tenant 授权锁序、锁后读取授权、幂等、审计及事件原子性。命令可靠性按动作后果判断；风险发布、整单发放等不能仅因被称作“台账”就省略关键保证。

### 3.3 权限与前端

权限判断共同包含租户/成员/应用有效性、动作许可、数据范围与对象状态。通用运行能力需要支持本人、部门与业务关系策略；仅有一个 organizationField 不足以完成 Q12。

业务关系策略由业务模块通过受控接口提供。列表、计数、候选、详情、写入、附件及导出使用同一业务边界；多角色范围可以合并，租户隔离与业务禁令仍然生效。导航和按钮不作为服务端授权证明。

工装目录、借用单和办理动作是不同资源/操作，分别执行对应策略：普通人员按目录权限查看可借工装，无需先成为该范围保管人；借用单按本人、历史部门或保管责任范围读取；发放与接收还需办理资格及禁止自办规则。同一业务边界指同种资源各入口一致，不是对所有资源使用同一过滤条件。

前端提供通用列表、查询、新增编辑、详情和主从组件；按路由加载实体定义及候选。解析器校验协议结构和受支持类型，不能把某个实体的完整字段集合写死。HTTP 模式失败不回退合成数据。

### 3.4 应用装配与可扩展边界

一个新应用应登记应用入口、菜单、实体定义、权限码、服务端绑定及必要业务命令，并提供自己的迁移、业务测试。它复用账号、组织、授权、附件、审计和可选流程能力，不复制这些实现。

“省力”不意味着无需业务建模、DDL 或测试。验收时记录新增和修改的文件类别；在冻结的台账能力上接入新普通实体及 Q8 字段变更，应无需为实体专门修改通用前后端源码。

本轮不抽象任意库存引擎、不新增在线表单设计器，也不要求先把所有安全台账迁入通用内核。

## 4. 工装借还模型及行为

### 4.1 对象与关系

| 对象 | 职责与关系 |
|---|---|
| 工装 Tool | 一件一个稳定 ID 和编码；名称/型号等描述、保管范围、可借资格及当前占用。独立生命周期 |
| 保管范围 CustodyScope | 业务责任边界，关联当前有资格的保管人；是否复用现有目录实体在实现前确认，不默认等于某个部门 |
| 借用单 Loan | 借用人、申请时部门、唯一保管范围、申请内容与定义版本、聚合版本 |
| 借用明细 LoanItem | 从属 Loan，引用 Tool；同单不能重复同一工装；保存发放及结清状态 |
| 归还批次 ReturnBatch / 明细 | 记录本次申请归还的哪些件及接收结果，支持分批；不得把整张借用单静默标成已归还 |
| 办理/异常记录 | 发放、接收、损坏和遗失结论、操作者、时间、理由与关联明细；只追加、可追溯 |

逻辑字段与表名为方案建议，最终 DDL 在契约、保管范围复用和迁移收敛后确定。所有业务关联保持租户一致。引用工装独立存在，删除或归档借用单不能级联删除工装。

### 4.2 办理链

1. 借用人提交一张同保管范围的申请，引用多件工装。申请不占用。
2. 发放前允许调整申请明细；改动必须受版本校验并保留修订。旧申请遇到字段升级的行为见 Q15。
3. 保管人整单发放：重新核验本人权限、范围、申请版本及全部工装可借状态；按稳定顺序锁定，任一不可借则整单不发放。申请本身不承诺未来可借。
4. 借用人选取部分或全部尚未结清明细申请归还。发起归还不是已接收，工装仍不能被其他单借出。
5. 保管人逐件确认接收，保存结果。正常接收后可借资格重新核验；损坏接收后为待处理、不可借。
6. 遗失由保管人记录结论后结清对应借还明细；遗失事实及责任记录继续保留，结案不代表免责，工装仍不可借。修理、赔偿及遗失后找回的完整流程不纳入首轮；未来恢复可借需明确授权动作，不能靠普通字段编辑恢复。
7. 全部明细均已正常接收、损坏接收或遗失结案时，借用单结清。单据结清不等于所有工装恢复可用。

同件工装只能有一个有效占用事实，由业务事务及数据库约束共同保证。归还请求不能重复覆盖已结清明细；重复提交按幂等契约返回原结果，异参冲突明确拒绝。发放后不能以撤销申请抹去实际借用，应继续走归还或异常处理。

### 4.3 已确认的责任与版本边界

| 问题 | 确认规则 | 状态 |
|---|---|---|
| Q13 保管人本人借用 | 可申请；发放、接收、遗失结论由同范围另一名有效保管人办理；缺人进入无人可办 | 已确认 |
| Q14 调岗与保管范围变化 | 旧单保留申请时部门及范围；借用人可办本人旧单，由当前负责原范围者办理；在借工装结清后再调范围 | 已确认 |
| Q15 字段发布后的旧申请 | 提交时绑定字段版本；旧申请继续原版，发放前调整明细保留修订并重校验；新申请使用新版，新必填不阻断旧单归还 | 已确认 |

Q15 不得改写已确认的 Q10：发放前可调整申请明细，不能无说明地改成一律撤销重建。

当前资格与历史归属分别判断：调岗不改旧单部门，但账号、成员及动作权限仍逐次验证；离岗保管人即使曾发放该单也不再有办理资格。旧单原部门主管按原部门范围查看，新部门主管不会仅因借用人调入就获得旧单权限。新增或更换原范围的保管人员属于授权变更，不是把工装转到另一保管范围。

### 4.4 命令与状态约束

以下为对已定流程的技术表达，不新增主管审批或库存业务。公开状态码在 D0 契约中固定，界面显示由单据及明细事实计算。

| 命令 | 状态和身份前提 | 原子结果 |
|---|---|---|
| 新建/编辑未提交申请 | 当前借用人、当前定义、尚未提交 | 校验同一保管范围及唯一工装；保存主从、并发版本及审计 |
| 提交申请 | 当前借用人；存在有效明细 | 固定本单定义版本及申请时部门/范围，转待发放；不占用工装 |
| 修改待发放申请 | 本单借用人、尚未发放、版本匹配 | 沿用本单定义版本，追加修订并重校验全部明细；不覆盖旧修订 |
| 撤销未发放申请 | 本单借用人、尚未发放 | 保留申请历史，结束待发放；不产生归还事实 |
| 整单发放 | 同范围有效保管人且非借用人；本单待发放；全部工装可借 | 记录发放，建立全部工装占用；任一失败全部回滚 |
| 申请分批归还 | 当前借用人；选中已发放、未结清且无待接收请求的明细 | 追加归还批次；保持实际占用，不改变为可借 |
| 正常/损坏接收 | 当前同范围保管人且非借用人；合法待接收明细 | 记录逐件接收并解除对应占用；损坏另记不可借状态；按全部明细结果判断结清 |
| 遗失结案 | 当前同范围保管人且非借用人；已发放且未结清的明细 | 追加遗失结论，结清该借还明细；保留责任与历史，工装不可借；关联待接收请求一并明确终结 |

所有命令重读当前资格、状态、记录版本和被引用对象。变更待发放明细与发放竞争时只允许基于当前修订的一方完成；迟到请求不得按旧明细发放。接收与遗失结案竞争时同一明细只能得到一个结清结果。标准编辑不能覆盖这些命令维护的字段。

工装可借资格与实际占用分开：可借由有效主数据、允许出借的物品状态及无有效占用共同决定。唯一有效占用记录是占用事实的权威来源；列表中的“可借/在借”是派生显示，不能再维护一个可独立修改的同义状态。损坏/遗失结清单据后仍不满足可借条件。

提交时冻结的申请字段版本用于本单后续编辑和展示；每次修改保存业务修订。冻结版本不冻结授权、当前工装可用性或保管人资格。未提交草稿按当前定义校验，遇到不兼容变化保留输入并提示重新核对，不自动按旧规则提交。

可借条件用于发放判断；已经借出的工装后来损坏，不阻止有权人员申请归还及办理损坏接收。每种动作分别校验自己的前提，不能把发放条件统一套到归还命令上。

## 5. 字段变更的具体验收

| 变化 | 预期行为 | 实施工件 |
|---|---|---|
| 工装新增可选描述字段 | 新定义的表单、详情和查询声明一致；旧数据为空，不虚构历史值 | 字段定义、类型列或已声明扩展的映射及迁移、契约测试 |
| 改标签、布局 | 稳定字段键不变，保存值不变；按需刷新受影响定义缓存 | 定义及展示验收，无无关表结构改动 |
| 已有字段增加查询能力 | 服务端校验、范围过滤、排序/分页与前端控件一致 | 字段查询声明；按实际查询需要增加索引并验证 |
| 可选改必填 | 对适用的可维护记录明确回填依据，回填后验证，再收紧约束；无依据时阻止发布而不猜值 | 版本定义、显式回填与约束迁移、失败/恢复证据 |

已冻结单据按其版本解释，不能因当前字段变必填而回写历史。普通当前主数据和冻结单据分开处理。旧查询视图引用删除字段时标失效，不静默丢条件扩大结果。旧页面提交不兼容定义时明确拒绝并保留输入，让用户刷新核对；不把普通主数据版本冲突和允许继续办理的历史单据混为一类。

需要区分数据库迁移版本、定义版本、聚合并发版本、业务修订和流程绑定版本。存在版本号不等于实现兼容处理；每种变更必须有实际数据升级与继续办理证据。

## 6. 实施顺序与出口

按已确认目标从 D0 顺序推进。各阶段以证据为出口，不承诺未测工期或吞吐；设计交付时尚未执行下面的代码和环境验收。后续执行结果见 [D0 验收记录](d0-closure-verification-2026-11-15.md)与 [D1 验收记录](d1-closure-verification-2026-11-15.md)，其余阶段不随之自动通过。

| 阶段 | 工作范围 | 出口证据 |
|---|---|---|
| D0 契约与分支收敛设计 | 保存现有工作，比较两条线的公共契约、迁移和权限；给出合并映射及迁移清单 | 唯一候选基线、兼容/冲突清单；隔离库可验证路径，原库保留策略 |
| D1 标准读写贯通 | 统一定义中的读取/创建/编辑及服务端绑定；以工装档案贯通页面、校验、持久化、范围与审计 | 新增/编辑/查询经真实 API 和数据库；禁止字段、撤权、冲突负例通过 |
| D2 主从与业务动作 | 借用单/明细、申请、整单发放、分批归还接收、异常结案 | 全链浏览器；并发抢同件只有一个成功，任一明细失败无部分发放 |
| D3 复用与变更证明 | 在公共能力冻结后登记另一个普通台账；执行 Q8 四类变更；与安全样板做契约对照 | 无实体专用通用层修改；已有数据、查询视图、旧单办理不被破坏 |
| D4 小步接回安全业务 | 选一个边界清楚的现有安全台账适配；随后再扩展流程/应用装配 | 既有业务行为回归、特殊授权及动作不被通用保存绕过 |

D3 的附加台账应是验证用的简单独立实体，不扩成第三个业务应用；可用工装类别等现有样板所需对象。工装借还是应用级验证，附加台账用于验证冻结后的新增成本。若接入发现公共能力缺口，先记录缺口并更新框架，再用新的样本复测，不能隐去额外修改后宣称零改动。

不因首轮优先读写能力而删除查询历史、个人视图、导出、事件、通知、设备接入等既有总需求。它们保持原需求追踪，按后续里程碑实施；本轮不能宣称整个 BR-002 或软件工厂已经完成。

## 7. 验收重点与证据边界

- **复用**：业务定义、映射、迁移、特殊动作与业务测试分别计量；普通新增台账及 Q8 变更不新增专用表单/控制器、不修改通用核心来识别实体名称。
- **授权**：本人、部门、保管范围的正反例；多角色叠加仍遵守业务禁令；列表、计数、候选、详情、写操作一致；跨租户不可见。
- **主从与竞争**：单内重复工装拒绝；不同保管范围拒绝；一件不可用导致整单不发放；同件并发发放与重复归还/接收有实库证据。
- **历史与升级**：修改标签不改字段身份；必填回填无可靠值时拒绝收紧；既有申请版本、明细修订、调岗和归还结果可解释。
- **异常**：损坏接收后单据可结清但工装不可借；遗失结论有权限和留痕；缺少办理人不跳过；网络提交未知不自动换键重复执行。
- **已有能力**：复用共用组件前先确认现有行为覆盖，缺少必要回归时补齐；不删改已执行迁移，不以字段元数据取代后端授权和业务校验。

单元/契约、架构边界、类型检查/构建、真实数据库、真实浏览器分别记录。核心能力公共测试可复用，但每个实体的绑定、权限范围、特殊规则和升级行为仍须验证。没有运行的检查记录 NOT_RUN，不沿用旧报告数字当本轮通过。

逐场景前置条件、动作、断言及证据类型见[台账与工装验收清单](software-factory-ledger-acceptance-2026-11-15.md)。该清单第 7 节记录后续阶段的实际覆盖与未执行项；设计完整性检查不能代替功能实现验收。

## 8. 与现有架构提案的修正关系

对 [architecture-proposal-2026-11-15.md](architecture-proposal-2026-11-15.md) 的修正关系如下。本次范围以已确认需求和本方案为依据，原提案保留作历史比较：

1. 从只读内核扩展为有限且明确的标准读写能力，补编辑、主从、关系策略和版本兼容；特殊业务命令仍显式实现。
2. 不把七个安全台账全部迁入作为先决条件，先验证普通台账、工装应用及字段变更，记录真实新增成本。
3. 权限内核不能只接受组织列；兼顾本人及业务责任关系，并保留逐动作规则。
4. T2 简化不省略全局授权锁；已有提交未知、恢复和事件原子性实现须先证明可替代，再考虑删除或归并。
5. 事件保留最小不可变业务事实；若按 ID/版本补查，读取对应历史版本，不能用当前值重解释旧事件。
6. 风险评估发布内容不可变，与“当前有效/被替代”的生命周期分别表达，解决整行不可改却更新 SUPERSEDED 的矛盾。
7. 不把重建现有库作为默认动作；先核验实际迁移历史和数据，再用隔离环境验证收敛方案。
