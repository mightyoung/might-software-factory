# D2 借用单范围查看切片

日期为 2026-11-19。本切片在逐件遗失结案和前端主题基线上，补齐部门及保管关系只读入口。D2 其他验收项沿用原清单逐项追踪。

## 实现

- `tool_loan.read` 的本人列表与详情继续按当前成员匹配申请人。
- 新增 `tool_loan_department.read`，依现有角色授权和组织范围匹配单据的申请时部门。成员同部门本身不产生这项权限。
- 新增 `tool_loan_custody.read`，依现有授权组织与当前有效的原保管范围关系共同过滤。
- 两类只读列表和详情复用相同 SQL 谓词，跨租户及范围外 ID 返回 404。列表按创建时间降序、ID 排序，最多返回 100 条。
- 前端增加“部门借用单”“保管范围借用单”，仅展示列表、逐件进度与只读详情。原办理命令逐次验证本人、保管关系和命令权限。
- V33 登记两项新权限。旧角色没有自动获得新权限，发布后由管理员明确配置数据范围。

## 验收证据

使用由 V32 合成测试库复制的独立 PostgreSQL 18 数据库 `msf_d2_read_scope_test`。通过真实 Flyway 应用 V33，后端专用 HTTPS 端口为 18484，前端同源端口为 15484。记录与截图输出在 `/private/tmp/msf-read-scope/acceptance/`。复现入口为 `tools/d2-read-scope/acceptance.py`。

浏览器用借用人真实申请一件工装，再由保管人真实发放。发放后在专用库将合成借用人的有效部门关系由 A 调到 B。重新登录后观察本人仍可读原单，原部门查看授权者可读，而 B 部门查看授权者无法读取该旧单。原单部门保持 A。

授权矩阵覆盖下列断言。

| 身份或变化 | 列表和详情结果 |
| --- | --- |
| 只有本人读取授权的借用人 | 新的部门、保管范围 API 均为 403，本人 API 仍可读 |
| 明确获得 A 部门查看授权的合成成员 | 能查看 A 部门原单，页面没有新建或修订按钮 |
| 明确获得 B 部门查看授权的成员 | 原 A 单不出现在列表，详情返回 404 |
| 有范围读取授权及当前有效关系的保管人 | 能查看原保管范围单据 |
| 获得保管范围查看授权但无保管关系的成员 | 列表过滤该单，详情返回 404 |
| 撤除保管人的有效关系 | 重新登录后列表过滤该单，详情返回 404 |
| 撤销部门查看授权 | 导航移除，直接 API 返回 403 |
| 通过另一租户的真实单据 ID 访问 | 列表不出现，详情返回 404 |
| 范围查看者直接调用发放或归还命令 | 403，旧单版本、逐件占用、修订和回执保持不变 |

针对纯 `department.read` 和纯 `custody.read` 的两项前端回归证明范围角色可以加载列表，避免依赖普通借用人的权限才能进入页面。工装前端 35 项测试、类型检查及 94 项迁移清单测试通过。

AU-03 的新范围列表、详情和办理负例已有本切片证据。AU-04 的本人原单读取与原部门可见已有证据，实际调岗后办理归还和更完整角色组合继续按总验收规格执行。AU-05 本次验证撤除关系后的范围读取，不替代新保管人实际接收旧单的全部验收。

## 调岗归还与保管交接补验

在同一独立 V33 测试库中，通过 Chrome 登录合成租户并调用同源 HTTPS API。每轮新建和发放一件工装。借用人从 A 调入 B 后，仍可归还自己的旧单；单据的申请部门保持 A，归还申请期间工装继续占用。

| 接收时的资格 | 实际结果 |
| --- | --- |
| 原保管人有接收权限，保管关系已到期 | 403 |
| 原保管人恢复原范围关系，管理员通过角色权限 API 撤销接收权限 | 403 |
| 新保管人经角色权限 API 获得接收权限，尚无原范围保管关系 | 403 |
| 新保管人同时具备接收权限与原范围有效保管关系 | 接收成功，单据结清，占用解除 |

每个拒绝阶段均对比单据、修订、回执、逐件记录和活动任务。成功后逐条关联创建、发放、归还和接收回执及成功审计；发放人仍是原保管人，接收人是新保管人。原保管范围未改，单据版本为 4，Flowable 历史实例已结束，活动任务数为零。

接收权限的撤销和授予经过平台角色管理 API，分别核对 permission_change_event 的管理员、目标角色、权限差异和跟踪 ID。调岗和保管关系生效时间通过专库 SQL 设置，这两类关系管理界面不在本轮验收范围。复现入口与运行条件见 [验收脚本说明](../tools/d2-read-scope/README.md)。
