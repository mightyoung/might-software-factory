# Finding read schema versions

The combined PR #10–#12 integration tree uses finding schema version 3. The version is returned by `GET /api/v1/entities/finding/schema` as `data.schemaVersion` and by finding list/detail responses as `meta.schemaVersion`.

PR #10 introduced schema version 2, adding `organizationId` and `organizationName`, expanding the default field projection, and changing the omitted-sort order to `createdAt DESC, id ASC`. The stacked field additions in PR #12 advance the combined representation to version 3. An explicit sort remains in effect; the server continues to append `id ASC` as a stable tie-breaker when needed.

Clients should key cached finding schema metadata by the caller's tenant/authorization scope, entity key, and `schemaVersion`; do not share schema cache entries across scopes. The version is a representation tag, not an authorization token. When a list/detail response reports a schema version different from the cached one, the client should discard that cached schema and refresh the schema endpoint before validating later queries or responses. Clear the cache when the session, tenant, or authorization scope changes. A schema version change also invalidates saved query field selections and defaults tied to the earlier version.

The finding OpenAPI schemas reject undeclared fields. A client that strictly validates a v1 or v2 response shape can reject fields added by a later version. This change does not negotiate or continue serving an older response. Before enabling the new backend response for such clients, coordinate a client update and regenerate its contract types. The checked frontend source contains generated API types and contract fixtures, but no finding-schema cache or runtime response validator was identified there; consumers outside this repository still need to be inventoried before rollout.
